2026-09-14：Protobuf 控制消息迁移及固定版本生成流程已完成，见 ADR-0021。核心回归、相关 race、约 31 万次控制解码 fuzz、重复生成一致性通过。独立旧 CBOR 对照中，64 人快照解码约 22.5 -> 11.2 微秒，完整消息 3393 -> 3603 字节；分配量增加，不声称全面性能胜出。语音格式与后台换钥保持；Noise 升到 exp-3、QUIC ALPN 升到 exp-2，需要匹配客户端 core/server。未提交或部署。

2026-09-14：已接入 server 每用户 mutex MPSC 环（覆盖旧语音、锁外编码入队），并实现 Noise exp-2 后台换钥，见 ADR-0020。相关四模块三轮 race 通过，真实回环 UDP 同一会话连续 32 次加速换钥期间保持双向数据报与可靠流；丢更新/确认包、同时换钥、重放/乱序、硬限额失败均有定向验证。尚需生产负载前后对照、长时间 WAN 与 Windows 实机体验，不据实验模型结果声称 server 性能提升。旧 UI 原型及 npm 构建已清理。客户端 core 与 server 需同步升级，未部署远端。

2026-09-12：已完成两轮“优化、部署、对照”：发送 worker 复用超时监视器；Noise UDP 写锁无竞争时跳过等待定时器。两版均经核心竞态测试、远程启动前后检查及 4/8 人公网测试，当前远程运行 `exp-20260912-gate`，旧容器保留用于回退。本机首项优化使 64 人分配速率中位数 14.55 -> 5.65 MiB/s；第二项在 4 人单轮中 0.091 -> 0.077 MiB/s，64 人收益很小。公网短测没有证明稳定的延迟改善。详见 [GC 验证](server-gc.md)；下一轮优先补丢弃/过期/接收计数及转发分段耗时，TS3 权限限制解除前不重试其多连接测试。

2026-09-12：完成独立 server GC 对照及 30 分钟 64 人/4 频道持续测试，见 [GC 验证](server-gc.md)。内存保持有界，但出现少量十几毫秒级 GC 暂停、约 219ms 转发长尾和约 0.042% 稳定成员缺包，尚未归因。后续优先评估逐包 context/timer 分配，保留有界写入与退出语义；补队列丢弃、过期、接收丢包及发送等待观测。尚未实施 pool 优化，也不据此决定 Rust 重写或宣称完成延迟验收。

2026-09-12：Noise UDP 已作为原生主实验接入，QUIC 为对照；两者共享频道、聊天、Opus 转发。仍需独立安全审查、自动换钥、语音拥塞适应、WAN 与容量验证；当前控制 stop-and-wait 不代表最终吞吐方案。详见 ADR-0019，不据此宣布性能优于 TS3 / QUIC。

2026-09-11：用户授权先启动原生 QUIC server，客户端过渡期保留 TS3 / Resona 协议选择，见 ADR-0018。本轮实现静态频道、访客昵称、可选共享密码、频道移动、文字与 Opus 转发；服务端不做 codec。回环网络与合成音频测试不代替 Windows 设备验收、WAN 丢包、长连接和容量压测。后续事项：原生成员提示音、账号与权限、动态频道、稳定协议格式（CBOR / Protobuf 评估）、客户端 Rust Opus 同参数基准。未据此完成完整服务端里程碑。

日期：2026-09-07。阶段顺序依据依赖与可验证性排列，不预估尚未探明的协议工作量。

终点是自有客户端、服务端和 Go 插件/机器人生态。TS3 是第一种兼容协议；将来的客户端和服务端需要各自验证 TS 互通。是否增加自研协议取决于测得的功能、性能和维护限制，不以提前替换协议为目标。

## M3：扩展与无界面机器人

- 先用内置音乐扩展验证事件订阅、命令注册、消息发送和音频注入接口。
- 同一 Go 客户端核心用于 GUI 和独立机器人入口。
- 拟定扩展能力、生命周期、版本和错误模型；插件不得绕过核心持有连接或身份私钥。
- 根据真实扩展需求引入进程隔离、权限授予和第三方 SDK。

验收：音乐扩展和一个自动化机器人通过同一扩展边界工作；禁用扩展会释放订阅和资源；失败不会破坏核心会话。

## M4：兼容服务端研究原型

- 明确首个兼容目标为特定版本普通 TS3 客户端的基本连接、频道、消息和语音。
- 实现服务端握手、会话、频道状态、权限、语音路由和持久化。
- 使用官方客户端、Resona 客户端交叉验证，不只验证自家两端。
- 将自有扩展通过能力协商接入；不能破坏约定的 TS3 基础兼容行为。
- 客户端与服务端保持各自的业务权威边界，只共享经过互通验证的协议组件和一致值类型。

验收：公开兼容矩阵与已知差异，完成权限隔离、资源限制和故障恢复验证。高可用、联邦、大规模集群均不在首个原型范围。

## 后续协议演进

- 记录 TS 兼容协议在功能、端到端延迟、可靠性和维护成本上的实际限制。
- 有明确收益时再提出自研协议 ADR，定义版本协商、迁移和客户端/服务端交叉测试方案。
- 保留经过验证的 TS 兼容适配，不把自研协议可用等同于 TS 兼容完成。

## 当前明确不做

- 不为尚不存在的服务端创建空微服务或通用基础设施仓库。
- 不把 TS3AudioBot HTTP API 固化为客户端核心模型。
- 不在启动时自动连接任意地址或采集麦克风；密码只在用户启用记住密码且认证成功后写入系统钥匙串，浏览器预览不保存密码。
- 不提前承诺第三方协议库的语音接收、平台覆盖或商业授权结论。
