# TS3 协议与未来服务端的优化空间

2026-09-10。这是基于本仓库实现与公开协议研究的评估，不是本项目服务端的性能测试，也不引入新的协议或实现任务。

## 当前协议形态

TS3将实时语音和可靠控制分开处理：语音走UDP，不为过时音频做可靠重传；命令在UDP上另有ACK、重传、排序、分片和压缩。控制正文为UTF-8命令及键值参数；文件传输使用独立TCP连接。本项目已接入Opus语音，内部以48kHz、960样本即20ms为一帧。

普通语音包相当紧凑：客户端方向13字节协议头加3字节语音头；服务端方向11加5字节，两者都是16字节，已包含8字节认证字段。不等同于端到端加密，也不代表可以删除认证字段。报文结构与语音/控制可靠性说明来自 [ReSpeak协议研究](https://github.com/ReSpeak/tsdeclarations/blob/master/ts3protocol.md)，该资料是独立逆向成果，不是TeamSpeak官方完整规范；仓库实现证据为 `third_party/teamspeak-go/transport/packet.go`、`transport/handler.go`、`commands.go`、`transfer.go`。本项目采用的上游及补丁见 `third_party/teamspeak-go/RESONA.md`。

按每20ms一包、IPv4无选项计算，16字节TS3开销加20字节IP和8字节UDP，共44字节；50包/秒对应17.6kbit/s。若编码音频平均32kbit/s，则该单向流约49.6kbit/s，不含链路层、隧道、心跳、控制流量和丢包冗余。IPv6基础头更大。此处是按协议字段推算，不是抓包实测；每个接收者也要承担转发流量。

## 值得优化的部分

语音包头没有大幅压缩的余地。举例每包再省4字节，在上述负载下只省1.6kbit/s；把两帧合并可以减少包数，但会增加等待和一次丢包影响的音频时长，不适合无条件用于电竞语音。

TS3控制层的文本字段、较小分片、会话引导和资源传输有改进空间，但通常不是稳定通话期间的主要带宽。是否值得替换，应测量入服时间、全量/增量事件字节数、资源缓存命中、包数与唤醒，不能把本地GUI IPC的重复快照开销归因于TS3线路协议。

## 服务端建议

先实现TS3兼容服务端时，线上格式仍必须遵循客户端预期，但内部实现可独立优化：

- 按频道维护接收集合和权限结果，避免每个音频包扫描全部用户。
- 在支持的编码组合下转发编码音频，避免无必要的解码、混音、重编码；各会话的加密处理仍需遵守协议。
- 有界队列、过期语音丢弃、减少分配和锁争用、复用缓冲，防止慢接收者拖住全频道。
- 合并定时器、按平台评估批量网络I/O、减少空闲唤醒；批处理必须设定实时延迟上限。
- 测量每活跃说话者到接收者的转发成本。多人同时说话时，流量随实际转发关系增长，仅更换语言不会消除它。

若未来测量证明兼容协议限制了目标，再给Resona客户端与服务端增加可协商的原生协议：重点评估增量订阅与断线恢复、资源内容哈希与缓存验证、紧凑控制编码、明确时间戳和弱网反馈、拥塞下的码率与FEC策略。安全传输采用成熟方案及库，不自行设计加密；QUIC等方案需要同负载对比CPU、内存、唤醒和时延，不能预设一定优于UDP。

验收应同时看P50/P95/P99端到端语音延迟、抖动与丢包恢复、每秒包数、空闲唤醒、每千次转发CPU成本、总内存及带宽。优先保持TS3互通，新的协议选型需单独ADR和测量证据。
