# Resona Development

- Branch names default to `feature/tsukiyo/{module}-{YYYYMMDD}_{task}` or the corresponding `fix/tsukiyo/` prefix. Use the shared owner name `tsukiyo`, never a model name or a `codex/` prefix. Example: `feature/tsukiyo/client-20260907_ts3-session`.
- Default model and effort: use GPT-6 Astra (`gpt-6-astra`) with `low` for ordinary features, GUI adjustments, routine fixes, and tests. Explicit user model/effort choices take precedence. Select by behavioral risk and unresolved uncertainty, not file count or task labels; a GUI change affecting cancellation or shutdown is lifecycle work.
- Use Astra `high` for TS3 handshake/protocol investigation, audio concurrency, cancellation/disconnect/shutdown lifecycle changes, cross-language ownership and IPC boundaries, architecture decisions, and difficult correctness reviews. Use `medium` for moderately coupled work that exceeds the low-effort scope but has no unresolved high-risk behavior; it is optional, not a mandatory step before `high`.
- Budget-oriented alternative: use GPT-5.6 Sol (`gpt-5.6-sol`) with `low` for mechanical, tightly scoped edits with explicit acceptance criteria, such as documentation, naming, or small presentation changes. Reserve `none`, when available, for deterministic text transformations that require no engineering judgment.
- Use Sol `medium` for budget-sensitive, well-specified local features, ordinary bug fixes, and focused tests where existing patterns establish the design. This is the default effort when selecting Sol for normal implementation.
- Use Sol `high` for bounded algorithmic reasoning, nontrivial local bugs, and focused reviews with clear contracts, especially when continuing a productive Sol task. For uncertain protocol, concurrency, lifecycle, or cross-module behavior, prefer Astra `high` rather than assuming more Sol reasoning replaces model capability.
- Sol `xhigh`/`max` and Astra `xhigh`/`max` are exceptional, not defaults. Use them for a concrete unresolved problem after `high` has produced a reproducible failure or conflicting evidence and at least one targeted investigation has not resolved it. State the remaining question and expected benefit; prefer `xhigh` before `max` unless evidence or the user justifies `max`. Compare switching from Sol to Astra before increasing Sol effort further.
- Escalate when verification exposes a race, broken invariant, repeated incorrect fix, or unresolved design conflict; do not wait for failures before assigning known high-risk work to Astra `high`. Return to the normal default for subsequent routine tasks once the difficult question is resolved. Slow output alone is not evidence that more reasoning is needed: check tool waits, runtime errors, service latency, and accumulated context first.
- When delegation is required or authorized, choose each subagent's model and effort by the same rules and its bounded responsibility; do not automatically give every subagent the main agent's expensive setting. Give each a concrete question, relevant evidence, and acceptance criteria. The main agent reviews and integrates the result.
- These are selection rules, not runtime configuration: use supported model controls when available, and do not claim a model/effort switch based only on this file or a prompt. Avoid interrupting useful work or forking solely to change effort; use a fresh task/fork when context or session recovery warrants it, with an explicit handoff of outstanding work.
- Selection basis (2026-09-08): Artificial Analysis Intelligence Index v4.3 suggests Astra `low` is a useful engineering cost/quality candidate relative to Sol `high`; this is not a measured Resona result. Evaluate cost per accepted change, elapsed time, retries, and review defects, including long-context/cache costs, rather than token prices or aggregate scores alone. References: [Astra vs Sol](https://artificialanalysis.ai/models/comparisons/gpt-6-astra-low-vs-gpt-5-6-sol-high), [Astra efforts](https://artificialanalysis.ai/models/releases/gpt-6-astra), [Sol efforts](https://artificialanalysis.ai/models/releases/gpt-5-6-sol).

- Product direction: an independent desktop GUI client, server, and Go ecosystem. TS3 is the first compatibility adapter for the client and a future compatible server; a native protocol may follow measured needs and a separate design decision. Plugins and bots build on protocol-independent behavior. TUI is not the current target.
- Desktop performance is a product constraint: target low total memory, background CPU and GPU interference during gaming. Compare release builds under equivalent workloads, including helper processes; do not infer performance from implementation language or package size. Keep decorative effects restrained. Evaluate native GUI alternatives with evidence before replacing Wails; see docs/frontend-evaluation.md.
- GUI maintenance (2026-09-10, ADR-0016): GPUI `desktop/` is the only product GUI. The user authorized retirement of Wails/`frontend/`; historical baselines remain in Git. HTML prototypes in `docs/ui-prototype/` are independent design tools, not product dependencies. Windows equivalent-workload and major workflow validation remain required; retirement does not establish a performance win. During minimized measurements, do not query/restore the app UI; see docs/wakeup-investigation.md.
- Read `docs/roadmap.md`, `docs/architecture.md`, and relevant ADRs before changing boundaries.
- Keep Go client behavior independent of Wails and frontend types. Centralize frontend bridge access.
- Clearly distinguish offline, local preview, and real network states. Never present simulated messages, voice, or connection success as real TS3 behavior.
- For GUI workflow changes, assign a product-experience subagent to review the full user flow: action, waiting, success, failure, cancellation, and exit. Record agreed behavior and acceptance criteria in `docs/product.md`; review implementation against them before delivery. Keep adjacent feature suggestions in the roadmap rather than silently expanding scope.
- Do not introduce protocol dependencies based only on README claims. Record the evaluated commit and actual integration evidence.
- Keep private identities, credentials, configuration, build artifacts, and local test data out of Git.
- Live tests on the user's TS3 server must stay inside a dedicated channel created by Resona for testing. Do not enter existing activity channels, change their settings, or operate other users. If creating the test channel or a required test action needs more permissions, report the specific denial and wait for the user to grant them. Normal login bootstrap is not permission to test in the default channel.
- Use `go test ./internal/...` for core changes, `cargo test --manifest-path desktop/Cargo.toml` and native build checks for desktop changes. Go checks no longer require HTML assets. For prototype-only changes, use `npm ci` and `npm run build` in `docs/ui-prototype/`.
- Update docs and ADRs when a decision changes. Mark roadmap items complete only with verification evidence.
- Do not create commits, change Git remotes, or push unless the user asks.
